# pona

**A GPT that actually speaks a language.** Toki Pona — ~130 words, 14 letters,
no inflection — is plausibly the first natural-ish language a studio-scale
model can get *right*, and "right" is machine-checkable: every number this
project reports comes from [telo misikeke](https://telo-misikeke.gitlab.io/)
(vendored, MIT, pinned), the community's grammar checker, judging raw
unresampled samples — daydream's oracle method transplanted from chess to
grammar. The end goal is a model you can *talk with* through a word-keyboard
UI: the word arm's ~368-token vocabulary is, literally, the keyboard.

## The research question

The Are.na correlation memo (§5.1) argued that **span, not Chomsky-hierarchy
position, predicts what a neural model finds hard**: glyph's outline codec is
a *regular* grammar (Type 3) and a 47.8M model still fails it 29% of the time,
losing the thread across 200+ character lines. Toki Pona is the inverse
configuration — a *context-free* grammar (Type 2, formally harder) whose
sentences average ~41 characters. pona is the falsification test:

- **null line** = `0.71^(41.3/200)` ≈ **93.2%** — the score a model with
  exactly glyph omni-xl's per-character error hazard would get here purely
  because sentences are short.
- Above the null → better per character despite the harder grammar (span
  thesis confirmed). Between 71% and the null → mixed. Below 71.0% → the
  hierarchy thesis wins.

The two arms make the test controlled as well as cross-project: same corpus,
same 6L/6H/192E body, same oracle, ~7 epochs each — but the char arm carries
every constraint across ~5× more sampling steps than the word arm.

## Corpus

Built by `data/fetch_*.py` → `data/build_corpus.py`; 6.93M chars after
filtering and dedup (gate: ≥500KB post-dedup). Every line passed
[sonatoki](https://pypi.org/project/sonatoki/)'s is-this-Toki-Pona filter at
sentence granularity; digits are excluded by policy (Toki Pona numbers are
words); near-dedup is name-blind, which collapses templated Wikipedia stubs.

| source | licence | kept |
|---|---|---|
| [Toki Pona Wikipedia](https://tok.wikipedia.org) | CC BY-SA | 1.83M chars |
| [poki Lapo](https://github.com/kulupu-lapo/poki), permissive subset only | per-work (audit: `data/poki_audit.json`) | 1.95M chars |
| [Tatoeba](https://tatoeba.org) `tok` | CC BY 2.0 FR | 3.16M chars |

**Excluded on principle:** the 6.39M-token `ma pona pi toki pona` Discord
scrape — the community never published its chat as a corpus (consent), and its
documented register drift would corrupt a grammar-checker metric in a way
indistinguishable from model failure. The corpus-relative denominator exists
for the drift that remains: the corpus itself passes the oracle at **96.0%**
(per-source: Tatoeba 99.0%, poki 96.9%, Wikipedia 86.9% —
`research/corpus_baseline.json`), so model scores are reported against that
ceiling, not against 100%.

Dialogue data for the chat round is generated by `data/gen_dialogue.py` —
every loaded LM Studio model × everyday topics via `tools/synthgen`
(ADR-0014), and **a dialogue survives only if every sentence passes the
oracle** with zero error-category issues. Provenance and per-model keep rates:
`data/dialogue_manifest.json`.

## Pipeline

```bash
uv run python projects/pona/data/fetch_wikipedia.py
uv run python projects/pona/data/fetch_tatoeba.py
uv run python projects/pona/data/fetch_poki.py
uv run python projects/pona/data/build_corpus.py          # filter + dedup + gate
uv run python projects/pona/oracle/fetch_oracle.py        # vendor the checker (pinned)
uv run python projects/pona/oracle/verify_oracle.py       # trust gate — must pass
uv run python projects/pona/research/score_corpus.py      # corpus baseline
uv run python projects/pona/data/prepare.py --arm char
uv run python projects/pona/data/prepare.py --arm word
uv run python core/nanogpt_core/train.py projects/pona/config/char.py
uv run python core/nanogpt_core/train.py projects/pona/config/word.py
uv run python projects/pona/harness.py --out_dir projects/pona/runs/char-r1
uv run python projects/pona/harness.py --out_dir projects/pona/runs/word-r1
```

## Leaderboard

| run | arm | val loss | first-try grammaticality (error-only) | corpus-relative | zone |
|---|---|---|---|---|---|
| char-r1 | char | 0.8082 | 92.3% [90.5, 93.8] | 96.2% | MIXED — CI straddles the 93.2% null |
| word-r1 | word | 2.5116 | **96.0%** [94.6, 97.0] | **100.0%** | **ABOVE NULL — span thesis confirmed** |
| chat-r1 | word + dialogue mix | 2.4574 | **96.9%** [95.6, 97.8] | **101.0%** | ABOVE NULL |

chat-r1 is the conversational candidate: replies to a fixed 20-prompt user-turn
set are **100.0% grammatical at t = 0.8** (98.8% at 1.0), 0% empty, 0% echo,
92% unique, on-topic — where word-r1 (no dialogue data) produces grammatical
non-sequiturs and 1.2% empties (`research/eval-*-replies-*.json`). Talk to it:
`uv run python projects/pona/talk.py --out_dir projects/pona/runs/chat-r1`.

Protocol: 1,000 raw unconditional sentences, t = 1.0, no top-k; oracle =
telo misikeke @ pin, error-category only (details in
`research/eval-*.json`). Val losses are in different units (per-char vs
per-word-token) — the harness numbers are the comparable ones. Per-char
hazard: char 0.194%, word 0.101%, glyph omni-xl 0.171% — same corpus, same
body, same grammar class, 5× shorter spans → hazard halves.
